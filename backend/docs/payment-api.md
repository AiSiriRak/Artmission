# Payment API Guide (read before using)

Audience: backend and frontend team members who integrate with order payment.
Provider: Slip2Go (PromptPay QR generation and slip verification).
Provider-level details are in [section 9, Provider notes](#9-provider-notes-slip2go). Full Slip2Go API docs: https://slip2go.com/guide.

## 1. Big picture

```
Artist accepts order
   └─ ConfirmOrder (DB transaction): order NOT_PAID + payment row PENDING
                                     qr_expire = accepted time + 24h, qr_payload = NULL
Customer opens payment page
   ├─ POST /orders/{id}/payment/qr      -> generate QR ONCE, store qr_payload
   ├─ GET  /orders/{id}/payment/qr      -> read stored QR (never generates)
   └─ (customer pays in banking app)
Customer uploads slip image
   └─ POST /orders/{id}/payment/verify  -> Slip2Go verifies -> payment HELD, order IN_PROCESS
Background worker (expiry sweep)
   └─ payment PENDING and qr_expire passed -> payment EXPIRED, order CANCEL, qr_payload = NULL
```

All three endpoints require a customer login (`Authorization: Bearer <access token>`) and the
customer must own the order. Auth role is `CUSTOMER`.

## 2. Design decisions (why the code looks like this)

| Decision | Reason |
|---|---|
| QR is **not** auto-generated by a worker | Auto generation wastes provider calls and resources. Generation is on demand via POST. |
| POST never creates a second QR | One payment per order (`payments.order_id` UNIQUE). If `qr_payload` already exists it is returned and Slip2Go is **not** called. |
| GET never calls Slip2Go | It is a cheap read. If no QR exists it returns 404 with a message. |
| Concurrent POSTs are serialized | A short-lived claim (`payments.qr_generating_at`, 30 s TTL) set by one conditional `UPDATE`; a contended request gets `409` (retry shortly). No DB connection or transaction is held during the provider call, and a crashed holder is superseded after the TTL. |
| Saving is conditional | `SaveQRPayload` only writes when payment is `PENDING`, `qr_payload IS NULL`, not expired, and order is `NOT_PAID`. |
| QR lifetime is 24h | `qr_expire` is set when the artist accepts the order. After that the order is cancelled automatically. |
| Slip upload (multipart), not image link | A link needs public storage and has URL-abuse risk. See [Provider notes](#9-provider-notes-slip2go). |
| Slip result is HTTP 200 with `success` | A rejected slip is a normal business outcome, so the UI reads `success` / `message` instead of handling an error status. |

Code map (all under `backend/internal`):

- `modules/payment/usecase.go` – `GetQR`, `GenerateQR`, `VerifySlip`, `ExpirePayments`
- `modules/payment/errors.go` – errors and `SlipRejection` reason mapping
- `handler/rest/payment_handler.go` – HTTP endpoints and response shapes
- `adapters/postgres/payment_repository.go` – QR generation claim, `SaveQRPayload`, `ExpirePayment`, `ConfirmSlipPayment`
- `adapters/slip2go/client.go` – provider client
- `worker/payment_qr.go` – expiry sweep

## 3. Payment and order status

| Payment status | Meaning | Order status |
|---|---|---|
| `PENDING` | Waiting for payment (QR may or may not be generated yet) | `NOT_PAID` |
| `HELD` | Slip verified, money held by the platform | `IN_PROCESS` |
| `EXPIRED` | QR expired without payment | `CANCEL` |
| `SETTLED` | Reserved for artist payout (not implemented) | – |
| `FAILED` | Reserved (not used yet) | – |

## 4. Endpoints

Base path: `/api/v1`. Replace `{order_id}` with the order UUID.

### 4.1 `POST /orders/{order_id}/payment/qr` – generate QR (once)

Call this when the customer opens the payment page. Safe to call repeatedly.

Response `200`:

```json
{
  "success": true,
  "message": "Payment QR generated successfully.",
  "already_generated": false,
  "payment_id": "…uuid…",
  "order_id": "…uuid…",
  "qr_payload": "000201010212…",
  "qr_expire": "2026-11-02T10:00:00Z"
}
```

If the QR already existed: `already_generated: true` and message
"Payment QR was already generated; returning the existing QR." (Slip2Go was not called.)
In both cases `qr_payload` is non-empty and usable.

### 4.2 `GET /orders/{order_id}/payment/qr` – read stored QR

Response `200`:

```json
{
  "success": true,
  "message": "Payment QR retrieved.",
  "payment_id": "…uuid…",
  "order_id": "…uuid…",
  "qr_payload": "000201010212…",
  "qr_expire": "2026-11-02T10:00:00Z"
}
```

### 4.3 `POST /orders/{order_id}/payment/verify` – verify slip

`Content-Type: multipart/form-data`, field `file` (JPEG, PNG or WebP, max 5 MiB). Example:
`const fd = new FormData(); fd.append("file", slipFile);` then `fetch(..., { method: "POST", body: fd, headers: { Authorization } })`
(do not set `Content-Type` manually).

Passed (`200`):

```json
{ "success": true, "message": "Payment verified successfully.",
  "order_id": "…", "payment_id": "…", "status": "HELD" }
```

Rejected slip (still `200`):

```json
{ "success": false, "reason": "AMOUNT_MISMATCH",
  "message": "Slip amount 100.00 THB does not match the order amount 150.00 THB.",
  "order_id": "…" }
```

`reason` values: `SLIP_ALREADY_USED`, `WRONG_RECEIVER`, `AMOUNT_MISMATCH`, `SLIP_NOT_FOUND`,
`SLIP_TOO_OLD` (slip made before the payment was created), `SLIP_FRAUD`, `INVALID_IMAGE`, `SLIP_REJECTED` (unknown provider code; the message includes it).
Always show `message` to the user; use `reason` only for logic. The provider code mapping is based
on Slip2Go docs we could not fully confirm, so verify it in the Slip2Go dashboard.

### 4.4 Error statuses

| Status | When |
|---|---|
| 401 | Missing or invalid token |
| 403 | Not a customer, or order not owned by caller |
| 404 | GET: QR not generated yet (call POST), or order not found |
| 409 | Order/payment state does not allow it, or another POST for this order is in progress (retry) |
| 410 | QR expired |
| 413 / 422 | Slip too large / missing / empty / wrong type |
| 500 | Provider outage or unexpected failure. QR generation can be retried, but may call the provider again after a timeout. Slip verification may require support recovery if the provider accepted the slip before recording failed. |

## 5. Showing `qr_payload` in the frontend

`qr_payload` is a **text string** (EMV PromptPay QR data), not an image. Render it as a QR code
in the browser. Do not send it through an `<img src>` directly.

Install a renderer, for example `qrcode.react`:

```bash
npm install qrcode.react
```

```tsx
import { QRCodeSVG } from "qrcode.react";

export function PaymentQR({ orderId, token }: { orderId: string; token: string }) {
  const [qr, setQr] = useState<{ qr_payload: string; qr_expire: string } | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    // POST is idempotent: it creates the QR the first time and returns it afterwards.
    fetch(`/api/v1/orders/${orderId}/payment/qr`, {
      method: "POST",
      headers: { Authorization: `Bearer ${token}` },
    })
      .then(async (r) => {
        const body = await r.json();
        if (!r.ok) throw new Error(body.detail ?? "Cannot load payment QR");
        setQr(body);
      })
      .catch((e) => setError(e.message));
  }, [orderId, token]);

  if (error) return <p>{error}</p>;
  if (!qr) return <p>Loading…</p>;
  return (
    <>
      <QRCodeSVG value={qr.qr_payload} size={256} marginSize={2} />
      <p>Pay before {new Date(qr.qr_expire).toLocaleString()}</p>
    </>
  );
}
```

Frontend rules:

1. Use POST to open the payment page, GET to refresh/reload. Never loop POST on a timer.
2. Show `qr_expire` as a countdown. After it passes, treat the order as cancelled (410/409).
3. Do not log or store `qr_payload` in localStorage; fetch it when needed.
4. After paying, the customer uploads the slip; branch on `success`:
   - `true` → go to the order status page (order is now `IN_PROCESS`).
   - `false` → show `message` and let the customer retry with a correct slip.
5. Disable the upload button while the request is running to avoid double submits.

## 7. Operations notes

- Config: Slip2Go secret key and receiver settings come from environment/config (see [Provider notes](#9-provider-notes-slip2go)).
- `adapters/slip2go/client.go` logs only status and provider code with `slog`, never request or response bodies.
- Slip2Go QR generation has no idempotency key; a timed-out POST that is retried manually may call
  the provider twice, but only one payload is ever stored.

## 9. Provider notes (Slip2Go)

- **Upload vs link:** we use the multipart upload endpoint `POST /verify-slip/qr-image/info`. The link
  endpoint (`qr-image-link`) needs publicly reachable storage and has URL-abuse risk. Revisit only if
  slips are already stored in object storage by another feature.
- **Amount format:** the QR-payload verify example documents an integer `checkAmount` (satang), while
  the image-upload example documents a decimal baht string (`"200.31"`). We use the decimal string with
  the upload endpoint (`formatSatang`). Do not assume the formats are interchangeable.
- **Verification conditions we send:** `checkDuplicate: true`, `checkReceiver` (our PromptPay account),
  `checkAmount eq`, and `checkDate gte` = the payment's `created_at` (UTC, ISO 8601). Slip timezone and
  second-precision handling against `gte` is not confirmed; test with a real slip made just after QR
  generation.
- **Limitations:** Slip2Go has no payout/refund API (a separate transfer provider is needed); QR
  generation has no idempotency key; a timeout means the result is unknown, so do not blindly retry.
  `checkDuplicate` marks a slip as used at Slip2Go before we record the payment; if recording fails the
  slip is burned, so the failure is logged with `order_id`, `payment_id` and `trans_ref` for manual recovery.
- **Response codes we rely on** (`payment/errors.go`):

| Code | Meaning | `reason` |
|---|---|---|
| `200000`, `200200` | Valid slip (amount re-checked locally) | - |
| `200401` | Wrong receiver | `WRONG_RECEIVER` |
| `200402` | Amount mismatch | `AMOUNT_MISMATCH` |
| `200403` | Slip older than the payment (`checkDate`) | `SLIP_TOO_OLD` |
| `200404` | Slip not found | `SLIP_NOT_FOUND` |
| `200500` | Fraud suspected | `SLIP_FRAUD` |
| `200501` | Duplicate slip | `SLIP_ALREADY_USED` |
| `400002` | Unreadable image | `INVALID_IMAGE` |
| other | Unknown | `SLIP_REJECTED` |
